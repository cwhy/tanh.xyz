Research note 03 · Structured decisions

Jev plays Craftax.

One typed question per tick, 210 ticks, five achievements, and a very specific way to die: facing a sapling, pressing the same button 128 times, with water five tiles away and the model's own priority answer reading drink. Telling it that the button did nothing does not help. Taking the button away triples the score.

Runs of 18 September 2026 · jev-1.13.0 · Craftax-Classic-Symbolic-v1 · seeds 0, 1, 2

What is plugged into what

TypeSafe serves a model called Jev that does not generate text. You send a state and a set of typed questions, and you get typed answers back: a Choice returns one option plus a probability for every option and a confidence, a Score returns a level on a scale you define, a Noul returns the probability that a statement is true. Every question in a request is evaluated in parallel, so asking twelve costs about what asking one costs.

Craftax is a survival-crafting environment written entirely in JAX — a reimplementation and extension of Crafter. Its classic variant has 17 actions, 22 achievements, and a 7×9 view around the player. It normally runs at hundreds of thousands of steps per second, which is the point of it: it exists so reinforcement learning agents can burn a billion steps overnight.

This demo throws that away on purpose. There is no training here, only inference, so a network round trip per step costs nothing but wall-clock time. One call per tick, one Choice over the 17 actions, and whatever comes back gets pressed. No planner, no pathfinding, no masking of actions whose requirements are not met.

The naive setting is the experiment. The question is not whether a typed decision model can be wired to a game loop — it can, in about 400 lines. The question is what breaks when a typed Choice is asked to be the policy instead of informing one.

The loop

The serializer is the only real work. Jev takes text — string, object, or array, no images — so the symbolic environment state becomes a JSON object with named fields: the local view as block names, the tile in front, vitals, inventory, bearings to anything interesting, and which achievements are still outstanding. This is step 180, trimmed:

{

    "note": "7 rows by 9 columns, you are at the centre; rows run top to bottom",
    "grid": [
      "water stone stone grass stone stone path  stone stone",
      "water path  tree  grass tree  stone path  stone stone",
      "water grass grass grass plant grass tree  tree  grass",
      "grass grass grass grass you   tree  grass grass tree",
      "grass grass grass grass grass crafting_table grass grass grass",
      "grass grass grass grass grass grass grass grass grass",
      "grass tree  tree  tree  grass grass grass zombie grass"

  },
  "facing": { "direction": "up", "tile_in_front": "plant" },
  "nearest": {
    "water": "1 up, 4 left (5 tiles)",
    "crafting_table": "1 down, 1 right (2 tiles)",
    "zombie": "3 down, 3 right (6 tiles)"
  },
  "vitals": { "health": 9, "food": 3, "drink": 1, "energy": 4, "max_for_each": 9 },
  "inventory": { "wood": 1, "sapling": 1, "wood_pickaxe": 1 },
  "world": { "time_of_day": "night", "timestep": 180 }
}

The policy is one question. Each option carries its own preconditions, so the model is not asked to remember Minecraft:

"action": Choice(
    instructions=(
        "You are the player in a survival crafting game. Pick the single action "
        "to take this tick. Stay alive, keep food, drink and energy up, and work "
        "towards the achievements still listed as remaining. An action whose "
        "requirements are not met does nothing, so only pick one you can do now."
    ),
    criteria={
        "DO": "Use the tile you are facing: chop a tree for wood, mine stone or coal "
              "(needs a wood pickaxe), ... drink from water, eat a cow or a ripe plant ...",
        "MAKE_STONE_PICKAXE": "Craft a stone pickaxe. Needs 1 wood, 1 stone and a "
                              "crafting table in reach.",
        ...
    },
)

Five more questions ride along for free: a priority Choice, a danger Score, and three Nouls. They change nothing — they are read only by the video. Keep that in mind for the next section.

The achievements were real and arrived early: wood at step 2, a crafting table at step 5, a wood pickaxe at 68, a sapling at 81, a planted sapling at 82. That is a competent opening. At a cent and a half per episode and a third of a second per decision, cost and latency are simply not the constraint — which is what makes the failure interesting rather than excusable.

Then it stopped

From step 82 — the tick after it planted the sapling — the agent faced that plant and pressed do for 128 consecutive steps, waiting for a plant that ripens on a timer it cannot see. 203 of the 210 actions in the episode were do. It died of thirst at step 209 with drink at zero, food at one, and health at one.

The striking part is not that it got stuck. It is that the rest of the response knew:

  • For 81 steps the priority question answered drink, mean confidence 0.61, rising to 0.86 by step 180.
  • Water was in the serialized view on every one of those 81 steps, and its bearing was in the state as plain text.
  • On all 81 of them the action question returned do, facing a plant.
  • It never once drank. collect_drink is the one early achievement it missed.

So the model was not wrong about the situation. It was wrong about the action — because "walk four tiles left and one up, then press do" is not something a single categorical choice over one-tile moves can express. Each individual step toward the water is locally worthless; only the sequence pays. A per-tick argmax over primitive actions has no way to price a plan, and the state carries no record of how long the current attempt has been failing.

Telling it what happened

The obvious repair is to close the loop: if do did nothing, say so, and it should stop pressing do. My first attempt at that appeared to refute the idea — same seed, last eight actions in the state, each tagged when nothing changed, and the result was worse: 2 achievements instead of 5, and 99% of actions still do.

That attempt was measuring the wrong thing. The tag compared whole states, so hunger ticking down, the light level falling and a zombie stepping sideways all counted as "something changed". During the stretch where every single do was useless, the tag fired on 53% of steps. The model was being told, in effect, that do works about half the time — and behaved accordingly.

The correct signal is the effect of the action, not the change in the world: an inventory delta, a changed block, damage to a mob, a move, a turn, a new achievement. Nothing else counts. That gives an exact phrase per transition, and a tally keyed by tile, facing and the block in front, so a recorded failure only applies while the situation is genuinely identical.

"feedback": {
  "note": "what your last actions actually did. 'nothing happened' means the
           action was wasted, so do not repeat it here",
  "recent": [
    "do -> nothing happened",
    "right -> only turned to face right",
    "do -> wood +1"
  ],
  "wasted_from_this_exact_spot": { "do": 12 }
}

With an honest signal, two things can be tested separately: telling the model an action was wasted, and removing that action from the options after it has done nothing three times in the same situation. The second is still raw action control — no goals, no pathfinding — it just stops offering a menu item that is provably inert. Three seeds each, 400-step cap:

SettingAchievements (s0, s1, s2)MeanReturndo shareMoves
Raw, no feedback5, 2, 23.02.194%6
+ exact feedback4, 2, 22.71.880%33
+ feedback, option removed after 3 failures11, 6, 67.76.828%137

Being told does not work. Being stopped does. Accurate feedback alone loosens the lock-in — repetition falls from 94% to 80% and the agent moves five times as much — but it converts repetition into wandering, and the achievement count does not improve. Reading "do → nothing happened" eight times in a row and then choosing do again is, apparently, well within reach.

Deleting the option changes the episode. Return triples, and six achievements appear that neither of the other settings ever reached on any seed: collect drink, eat cow, defeat zombie, collect stone, place stone, collect coal. Every one of them requires walking somewhere first. The suppression does not teach the agent to navigate — it just stops the free ride, and a policy that cannot stand still has to go somewhere.

Pick dead options removed in the replay above to watch this seed with the rule on: wood at step 2, table at 8, wood pickaxe at 18, a cow eaten at 80, water drunk at 103, a zombie killed at 118, stone at 177, coal at 193. It still dies at step 197 — but at full drink and mid food, to a mob rather than to thirst. Removed options are struck through in the bar list on the ticks where the rule fired.

This is not sound, and that is fine. Craftax changes on its own: the sapling that is inert now ripens later. Suppression after three identical failures, cleared whenever the block in front changes, is a heuristic that trades a small amount of correctness for not dying of thirst beside a pond. A note worth keeping for anything that gates a model's options this way.

Whose knowledge is it

Everything above runs on a state I engineered. The bearings list is the set of things I decided were worth pointing at. workstations_in_reach encodes Craftax's adjacency rule. The tile in front is resolved before the model sees it. The remaining achievements are handed over as a to-do list. And the action options spell out the whole tech tree — one wood and a table makes a pickaxe, iron needs a furnace. A fair question is how much of the behaviour was ever the model's.

So: strip it. The raw state is the observation and the body — the 7×9 grid of block names, which way you face, health, food, drink, energy, what is in the bag, the light level, the achievements you have. No bearings, no reach flags, no resolved tile, no to-do list. Each action gets one neutral sentence about what the button does and nothing about when to press it: "DO": "Interact with the tile you are facing.", "MAKE_IRON_PICKAXE": "Craft an iron pickaxe." No recipes, no requirements, no advice.

Then the missing context comes back as observation rather than instruction: the last sixteen transitions, each as what was pressed and what it did, plus the count of what has already been wasted from this exact spot. That is history, not game knowledge — it is derived from watching, and the model is still the one deciding.

Take the priors away with nothing in their place and it collapses: 3.0 achievements down to 1.0, and a return of essentially zero. The hand-written context was carrying the run.

Give it history instead and it comes back past where it started — 4.0 against 3.0 — with no Craftax rule anywhere in the request, and on 23% fewer tokens per step. Sixteen lines of "I pressed this, that happened" are worth more than my curated bearings and my to-do list. That is the result I did not expect.

But look at which achievements. Across all three seeds, no raw agent ever placed a crafting table or made a pickaxe. What they did instead was drink, fight a zombie, kill a skeleton, plant a sapling. The raw agents survive; they never craft. Crafting is the one part of Craftax that cannot be induced from looking at the tiles — the recipes are arbitrary and invisible — so it is exactly the part that disappears with the tech tree. The priors were not buying general competence. They were buying the recipes, and nothing else.

How much to read into this: three seeds per arm, one model version, a 400-step cap. A one-achievement gap is noise. The 1.0 / 4.0 / 7.7 spread is not, and the crafting split is categorical — zero occurrences across three raw seeds against every engineered seed.

The best arm is still the engineered one with dead options removed, at 7.7. Purity costs about a third of the score. What it buys is knowing that the number belongs to the model rather than to my prompt.

Letting it keep notes

Sixteen steps of history is an arbitrary window, and a sliding window forgets by construction. So: give the model a memory and let it decide what goes in. One more Noul rides in the same call — the transition in last_transition is worth writing into long-term memory; ordinary movement that taught nothing is not — and code does only the bookkeeping. Identical entries merge into a count, and when the store is full the lowest-scored entry is dropped. The threshold is 0.5, the midpoint of a probability, rather than a number I tuned.

The curation works. It writes on about 14% of ticks, and what survives is exactly what you would want a player to have learned:

facing tree:  do -> wood +1          (happened 4 times)
facing grass: do -> sapling +1       (happened 7 times)
facing cow:   do -> unlocked an achievement
facing grass: do -> nothing happened (happened 5 times)

That is the mechanics of the game, discovered by pressing buttons rather than read from a recipe list. It is the most convincing artefact in this whole note. It also does not help — and before the table, it is worth being straight about how much of that store is really the model's.

Two priors smuggled back in. Each entry is written as facing <tile>: <action> -> <effect>. The facing tile is computed in code from the direction offsets — the Craftax rule that your heading selects the tile your actions act on. I deleted that from the raw state as engineered context and then put it back inside every remembered line, and it is exactly what makes facing tree: do -> wood +1 generalise to every tree in the world. The effect phrase is mine too: a hand-written list of which variables count as action-caused, which is what separates a real effect from hunger ticking down. Both run through the failure tally as well, so the suppression rule inherits them. What is genuinely the model's is which transitions are worth keeping — not the vocabulary they are written in.

No variant beats the plain window, and with standard deviations above 1 achievement none of the gaps is individually significant either. What is clear is that adding memory did not buy anything, and cost 14% more tokens per step to do it.

The reason is visible in the store. Deduplication collapses it to six or seven distinct entries, and every one of them is a rule — what a button does to a kind of tile. Rules are precisely what the last sixteen steps already show, so the memory is mostly a slower copy of the window. What a window genuinely cannot hold is a place: the pond you passed forty steps ago.

So I gave the raw state a sense of place — absolute x, y on the 48×48 world — and let memory entries carry coordinates. That went worse, and instructively. Every entry became unique, so nothing merged, and the store filled with one-offs that will never recur:

at (32,29) facing grass: down -> hit a mob
at (32,43) facing grass: up   -> hit a mob
at (32,50) facing water: do   -> hit a mob (happened 6 times)
at (32,28) facing stone: down -> hit a mob

Coordinates destroyed the generalisation that made the first store useful. A memory of "do on a tree gives wood" transfers to every tree in the world; a memory of "at (32,29) something hit me" transfers to nothing, and it crowds out the rule it displaced.

What this says: the bottleneck was never how much the agent remembers. It forgets nothing important inside sixteen steps. Every intervention that gave it more to know — exact feedback, a curated memory, coordinates — moved the score by less than the seed noise. The one intervention that moved it by a factor of two was the one that took an action away. Knowing and doing are separate problems here, and only the second one was ever binding.

Closing the leaks

So I closed both. The effect phrase is now a diff of the observation the model already receives, with no opinion about what caused it — view r2c4 tree->grass, wood 0->1 rather than wood +1. The situation key is the visible surroundings and the heading, with no notion of a tile in front. Nothing in the feedback names a Craftax rule any more.

Purity is expensive: 4.2 down to 1.8, more than half the score, for two pieces of phrasing. And the mechanism is legible in the transitions. Without a rule about what an action is able to cause, the diff cannot separate the action from the clock:

do -> nothing you can see changed
do -> nothing you can see changed
do -> energy 8->7
do -> drink 7->6

Those last two read as though pressing do drained the player. It did not; time did. The curated vocabulary was not decoration — deciding which variables an action can move is the content of the signal, and it is the same distinction whose absence produced the 53% mislabelling at the start of this note.

Then the reversal. Memory hurt when the feedback carried my priors (4.2 → 2.7) and helped once they were gone (1.8 → 2.6). It was redundant with the engineered vocabulary and substitutes for it: a store that re-derives the rules is worth something only when the rules are not already being handed over on every line.

And it does re-derive them. Here is what the prior-free agent wrote down for itself:

do -> view r2c4 tree->grass, wood 0->1, achievement collect_wood
do -> view r5c5 skeleton->path, view r6c5 path->skeleton
do -> view r6c5 skeleton->path, health 9->7

Cell r2c4 is one row above the centre, which is where the player stands. The model has written down, in raw view coordinates, the rule I deleted: the cell in front of you is the one that changes, and when it was a tree you end up holding wood. It recovered the prior from observation — it just does not recover enough of it, fast enough, to pay for what removing it cost.

Which raises the obvious question: why a window at all? A transition line is about fifty characters, so recording every state change since the episode began costs a few thousand tokens even at step 400 — trivially affordable. Consecutive identical lines collapse to (x12 in a row), so a stuck stretch stays cheap. I ran it: complete recall, nothing thrown away.

Complete recall is the worst of the three. Hundreds of near-identical movement lines bury the handful that matter, and the agent wanders longer — 231 steps on average — while achieving less. Truncation beats completeness, and selection beats truncation: the ordering is exactly the argument for letting the model curate, which is the one thing the memory experiment had failed to demonstrate while the engineered vocabulary was still propping the window up.

The other axis is resolution. Each transition above is a digest: the effect line lists changed cells only up to a handful, then summarises the rest as view changed in 25 places. Worse, the engineered version reported the first thing it found and dropped the rest, so do -> wood +1 silently hid that the tile in front had turned from tree to grass. Recording every change instead — every cell, every vital, every item, in one line per step — costs 24% more tokens and scores 2.2 against 2.6, which is inside the noise.

The reason completeness buys so little is an artefact of the view being egocentric. One step of walking rewrites roughly thirty cells, because the window scrolled, not because the world moved. A complete diff cannot tell those apart, so most of what it adds is the agent's own motion. The informative part of a transition — the single cell in front that turned from tree to grass — arrives buried in thirty lines of parallax. What the memory kept is the tell:

do -> view r4c4 tree->grass, wood 0->1, achievement collect_wood
do -> view r4c4 tree->grass, wood 1->2
do -> drink 8->9, achievement collect_drink

Every entry it chose to keep is a transition where the diff was small. The complete diffs of movement, thirty cells wide, were never worth remembering, and the model never kept one.

Where that leaves the number. The honest prior-free score is 2.6 achievements out of 22, against 4.2 with two phrases of Craftax knowledge and 7.7 for the engineered state with dead options removed. Everything above the 2.6 is mine, not the model's. That is the figure I would quote.

What I would build instead

Removing dead options is a patch on the symptom, and it works well enough to triple the return. The underlying shape of the problem is unchanged: the diagnostic questions were reliable while the action question was not, and the API's own documentation points at the arrangement that would exploit that. TypeSafe's line is to keep code in control and give the model narrow, structured decisions. Both the original failure and the size of the repair landed where the docs say they will.

The version I would ship keeps the same single call and changes what is asked of it:

  • Choice picks a subgoal, not a keystroke — drink, gather wood, flee, craft a stone pickaxe. That is one decision per goal, not one per tile of walking.
  • Code does the locomotion. A breadth-first search to the nearest matching tile turns "drink" into a concrete sequence of moves, and the Craftax tech tree is a deterministic precondition check, not a judgment call.
  • Replan on events — goal achieved, goal invalidated, damage taken. That is roughly one call every 10–30 ticks, not 210 calls for 210 ticks.
  • Gate on confidence. A mean of 0.34 on the action question was the model reporting, correctly, that it did not have a clear read. Nothing in this demo listened to it.

None of that is a workaround for a missing feature. It is the difference between asking a decision model to choose and asking it to drive.

Reproduce

The agent is four files in scripts/craftax_jev/: the serializer, the question set, the loop, and the video compositor. It reads JEV_API_KEY from the untracked .env at the repo root.

uv venv --python 3.12 .venv
uv pip install --python .venv/bin/python craftax typesafe-sdk imageio matplotlib

.venv/bin/python agent.py --steps 600 --seed 0 --out runs/run-01
.venv/bin/python make_video.py runs/run-01 --fps 6

Add --history 8 for the second variant. Every run writes decisions.jsonl with the full request state and response body for each step, which is what both the video and every number above are drawn from.
